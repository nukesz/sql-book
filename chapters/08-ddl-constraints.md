# 8. Constraints and DDL

**You will learn:** creating and altering tables, and using constraints to make bad data impossible.

## Principle: let the database enforce the rules

Application code has bugs, there may be more than one application, and people run ad-hoc scripts. A constraint is the only validation that **cannot be bypassed**.

## CREATE TABLE

```sql
CREATE TABLE reviews (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_id  bigint  NOT NULL REFERENCES products (id) ON DELETE CASCADE,
    customer_id bigint  NOT NULL REFERENCES customers (id),
    rating      int     NOT NULL CHECK (rating BETWEEN 1 AND 5),
    body        text,
    created_at  timestamptz NOT NULL DEFAULT now(),
    UNIQUE (product_id, customer_id)          -- one review per customer per product
);
```

## The constraint toolbox

| Constraint | Guarantees |
|---|---|
| `NOT NULL` | value present |
| `DEFAULT expr` | value if omitted (not a constraint, but related) |
| `PRIMARY KEY` | `UNIQUE` + `NOT NULL`, one per table |
| `UNIQUE` | no duplicates (creates an index) |
| `CHECK (cond)` | row-level rule (`price >= 0`) |
| `FOREIGN KEY` | referenced row exists |
| `EXCLUDE` | no two rows "overlap" (e.g. room bookings; advanced) |

Name constraints for readable errors and easier changes:

```sql
ALTER TABLE products ADD CONSTRAINT products_price_nonneg CHECK (price >= 0);
```

Constraint names are schema-wide identifiers for some object types and appear in error messages. A useful convention is `<table>_<columns>_<kind>`, such as `reviews_rating_check`.

### Foreign key actions

```sql
REFERENCES products (id) ON DELETE CASCADE      -- delete children with parent
                         ON DELETE SET NULL     -- column must be nullable
                         ON DELETE RESTRICT     -- error (default is NO ACTION: same, but checked at statement end)
                         ON UPDATE CASCADE
```

`CASCADE` is convenient and dangerous: one `DELETE` can remove thousands of rows. Use it for true "part-of" relationships (items of an order), not for business entities.

> Important: PostgreSQL does **not** automatically index the referencing (child) column of a foreign key. Index `orders.customer_id` yourself; otherwise deleting a customer or joining orders → customers can scan the whole table. See chapter 13.

## ALTER TABLE

```sql
ALTER TABLE customers ADD COLUMN birthday date;
ALTER TABLE customers ALTER COLUMN country SET DEFAULT 'HU';
ALTER TABLE customers RENAME COLUMN birthday TO birth_date;
ALTER TABLE customers ALTER COLUMN name TYPE varchar(200);
ALTER TABLE customers DROP COLUMN birth_date;
ALTER TABLE reviews RENAME TO product_reviews;
DROP TABLE product_reviews;            -- add IF EXISTS for scripts
```

DDL is **transactional** in PostgreSQL: you can `BEGIN; ALTER ...; ROLLBACK;`. This is a superpower for safe migrations (few other databases offer it).

### Adding NOT NULL to an existing column

```sql
ALTER TABLE customers ADD COLUMN segment text;                         -- nullable first
UPDATE customers SET segment = 'standard' WHERE segment IS NULL;       -- backfill
ALTER TABLE customers ALTER COLUMN segment SET NOT NULL;               -- then enforce
```

On big, busy tables, schema changes take locks. Chapter 23 covers doing it without downtime.

## Identity, sequences, UUIDs

- `GENERATED ALWAYS AS IDENTITY` is the modern auto-increment (preferred over `serial`). Values come from a sequence; **sequences have gaps** (rolled-back inserts still consume numbers). Never rely on gap-free ids.
- `uuid` keys (`gen_random_uuid()`) are good when ids are generated by clients or must not be guessable; random UUIDs index less efficiently than sequential ids. `uuidv7()` exists from PG 18.

## Schemas

```sql
CREATE SCHEMA reporting;
CREATE TABLE reporting.daily_sales (day date PRIMARY KEY, total numeric);
SHOW search_path;           -- "$user", public
```

Use schemas to group objects and to apply permissions per group.

## Exercises

1. Create `reviews` as above. Insert a valid review and try to violate each constraint (rating 6, duplicate review, nonexistent product). Read the error messages.
2. Delete a product that has reviews. What happens with `ON DELETE CASCADE`? What would happen with `RESTRICT`?
3. Consider the rule "`orders.created_at` must not be in the future." Why is `CHECK (created_at <= now())` a poor way to enforce it? Where could that rule live instead?
4. Add a nullable `email_verified_at` to `customers`. Then write the sequence of steps to make a `status text NOT NULL DEFAULT 'active'` column safe on an existing table.
5. Prove that DDL is transactional: begin, drop `reviews`, check it's gone, roll back, check it's back.
6. Create a partial unique index so that a customer can have at most one `new` order at a time. (Syntax: `CREATE UNIQUE INDEX ... WHERE ...`; see chapter 13.)
